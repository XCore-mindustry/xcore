заморозку серверов, и этап 3 — карта как сущность (`map_entities` с ключом по посту) и

Затрагивает: Discord-бот (этапы 0–1), `xcore-protocol` и `XCore-plugin` (этапы 2–3).
Связанные документы: [ревью карт в кейсах, раздел 9.5](cases-design-spec.md),

## 1. Зачем

Предложение новой карты продумано: пост на форуме, автоматические проверки, карточка, «Принять»
ставит карту на сервер. Обновление уже принятой карты не продумано вообще, а ручные команды
`/maps upload` и `/maps remove` живут отдельно от ревью. Меню местами неудобные.

Случай, с которого начался этот документ (кейс #2112, карта для mini-pvp):

1. Автор выложил карту в пост. Ревьюер поставил её командой `/maps upload` прямо в посте, а не
   кнопкой «Принять». Кейс остался открытым, создатель не проставился.
2. Через пять дней автор выложил в тот же пост обновление. Файл назывался иначе
   (`… (1).msav`). Другой ревьюер нажал «Принять», считая, что бот обновит карту. Бот поставил
   вторую карту рядом с первой.
3. Старый файл удалили вручную. Заодно, по аналогии, удалили одноимённую карту другого автора,
   которая дубликатом не была. Вернуть её штатно нельзя.

## 2. Что сломано

1. **Обновление в уже принятом посте бот молча игнорирует.** Кейс привязан к посту навсегда:
   и идентификатор подачи, и ключ дедупликации равны `map:<thread id>`
   (`cases/flows/maps.py:222`). Новые файлы читаются только пока кейс открыт
   (`cases/flows/maps.py:263`). В случае выше обновление обработалось лишь потому, что кейс по
   ошибке остался открытым. Правильный путь дал бы худший результат.
2. **Отклонённый пост блокируется** (`cases/threads.py:511`). Исправленную версию туда не
   выложить, автору остаётся создавать новый пост.
3. **Нет понятия «заменить».** Карта ставится под именем вложения
   (`cases/flows/maps.py:605`, `event/transport/MapTransportHandler.java:357`). Имя изменилось —
   рядом появляется вторая карта. Имя совпало с чужой картой — она перезаписывается без
   предупреждения.
4. **`/maps upload` не знает о кейсах** (`handlers_maps.py:362`). Кейс не закрывается, создатель
   по умолчанию не проставляется, значок Map Maker не выдаётся, тег поста не меняется.
5. **Удаление вслепую и без отката.** Подтверждение показывает только имя файла
   (`handlers_maps.py:330`): ни автора, ни того, кто и когда залил, ни ссылки на ревью. Файл
   стирается с диска, копии не остаётся. В аудит бота удаление не пишется.
6. **Статистика ищется по имени файла, потом по «название + автор»**
   (`database/repository/MapDataRepository.java:158`, тот же порядок в
   `MapTransportHandler.java:148`). Два файла с одинаковым названием и автором делят одну запись,
   поэтому в списке у обоих одинаковые лайки. Две разные карты с одинаковым названием и автором
   делили бы голоса так же.
7. **Меню и тексты.**
   - «Принять» — цепочка из двух–четырёх отдельных вопросов (сервер, «принять с ошибками»,
     «принять без глубоких проверок»), и только один сервер за раз.
   - `/maps upload` и `/maps remove` целиком на английском (`handlers_maps.py:317-359`,
     `419-426`), остальное переведено.
   - К переведённому предупреждению дописывается английский текст от сервера
     (`cases/flows/maps.py:851`).
   - Карточка ревью не показывает, что уже стоит на серверах, поэтому ревьюеру приходится искать
     файл руками.
   - После принятия на карточке до 30 дней висит строка про ожидающий значок.

## 3. Модель

**Карта — это пост на форуме, файл — её ревизия.** Каждая ревизия получает свой кейс в том же
посте. Одновременно открыт максимум один: уникальный индекс по `dedup_key` уже действует только
для активных кейсов. Идентификатор подачи первой ревизии остаётся `map:<thread id>`, следующих —
`map:<thread id>:<attachment id>`.

**Обновление ставится под тем же именем файла, что уже на сервере.** Тогда запись статистики,
лайки и строка в `map_uploads` остаются теми же, в `map_upload_history` добавляется новый снимок,
дубликат не появляется. Протокол для этого менять не нужно: в `maps.upload.request` адрес файла и
целевое имя уже раздельные поля (`MapFileSourceV1.url`, `fileName`).

**Перед любой установкой бот сверяется с `maps.list` целевого сервера.** Ответ уже содержит
название, автора и SHA-256 каждого файла. Ревьюер видит один из четырёх вариантов:

| Что нашлось на сервере | Что предлагает бот |
| --- | --- |
| Файл с тем же SHA-256 | Уже установлена; «Принять» перезаписывает те же байты и чинит атрибуцию |
| Файл из прошлой принятой ревизии этого поста | Обновление, целевое имя подставлено |
| То же название и автор либо то же имя файла, но другой пост | Ревьюер явно выбирает: «заменить X» или «поставить отдельно под другим именем» |
| Совпадений нет | Новая карта |

Какие файлы относятся к посту, бот выводит из уже хранимого: `payload.sha256` и
`resolution.server` / `resolution.file_name` принятых кейсов этого поста. Отдельной коллекции на
этапах 0–1 не требуется.

**Откат — переустановка вложения прошлой ревизии.** Кейс хранит сообщение, вложение и хэш каждой
проверенной ревизии, поэтому для карт с форума откат не требует ничего от сервера. Для карт,
поставленных мимо форума, нужна копия удалённого файла (этап 0, пункт 4).

## 4. План

### Этап 0 — быстрые правки, только бот

Реализован. Сверка — `map_targets.py`; `/maps upload`, `/maps remove`, `/maps duplicates` —
`map_admin.py`; копии удалённых карт и кнопка «Вернуть» — `map_backups.py` (коллекция
`map_removals`); выбор замены в «Принять» — `cases/flows/maps.py`. Отличия от описания ниже:

- Запись об удалении с копией файла и кнопкой «Вернуть» публикуется в канале, где выполнили
  команду; лог-канал (`DISCORD_MAPS_LOG_CHANNEL_ID`, по умолчанию выключен) получает строку со
  ссылкой. Без лог-канала поведение то же, что раньше, — публичное сообщение в канале команды.
- «Вернуть» отказывается, если имя файла на сервере уже занято: перезапись — новое решение.
  Вернувший записывается загрузившим, создатель берётся из атрибуции удалённой карты.
- Если сервер не прислал список карт, `/maps upload` грузит без сверки и пишет об этом в
  результате, а «Принять» спрашивает подтверждение.
- Из подробностей находок убран английский текст сервера только там, где он повторяет перевод
  (`missing-name`, `missing-author`, `data-patches`, `no-spawn`, `pvp-single-team`); где в
  подробностях есть данные (моды, размеры, координаты), они остались.

1. Сверка с сервером в «Принять» и в `/maps upload` по таблице из раздела 3. Тихих дублей и
   тихой перезаписи чужой карты больше нет.
2. Вариант «Заменить `X`» в «Принять» и параметр `replace:` у `/maps upload` (автодополнение по
   установленным картам). Файл уходит на сервер под именем заменяемого.
3. `/maps remove`: вместо имени файла — карточка карты (название, автор в файле, создатель, кто и
   когда залил, размер, оценки, превью, ссылка на пост с ревью) и предупреждение, если на сервере
   есть другие файлы с тем же названием. Подтверждение видит только тот, кто удаляет.
4. Перед удалением бот забирает файл через существующий `maps.file.request` и публикует его в
   лог-канале карт вместе с записью «кто, что, откуда, почему» и кнопкой «Вернуть». Туда же
   пишутся установки и замены.
5. Локализация `/maps upload` и `/maps remove` (en, ru, uk). Английский текст от сервера
   показывается только для кодов, которых нет в переводе.
6. `/maps duplicates <server>`: группы файлов с одинаковым хэшем либо одинаковым названием и
   автором — для разовой чистки накопившегося.

### Этап 1 — обновления как ревизии, бот

Реализован. Отличия от описания ниже и подробности:

- Ревизия — отдельная заявка в том же посте: `submission_id` первой — `map:<thread>`, следующих —
  `map:<thread>:<attachment>`, `dedup_key` общий, поэтому открыта максимум одна. В `payload`:
  `revision`, `previous` (номер, статус и то, с чем сравнивает карточка) и `installed` (где стоит
  последняя принятая версия поста).
- Уникальный индекс `discord.thread_id` теперь действует только среди открытых заявок
  (`discord.thread_id_open`); старый индекс удаляется при первом запуске этой версии.
- «Принять» — по-прежнему выбор сервера, затем одно подтверждение: сервер с прошлой версией идёт
  первым и подписан «обновить `file`», цель подставляется сама, ошибки и незавершённые проверки
  собраны в один вопрос. Отдельной панели не делал: при подставленной цели это два клика.
- Откат — команда `/maps rollback` в посте, а не кнопка: у закрытой заявки кнопок нет. Откат
  пишется заметкой в пост и в лог карт, но не в аудит кейсов.
- `/maps upload` файла, который сейчас на проверке в этом посте, ничего не грузит и показывает
  номер заявки.
- Фикс чужой карты (решение 3): создатель берётся из атрибуции заменяемой карты, автор поста
  записывается как исправивший (`payload.fixer`) — в карточке заявки и в `/map`. Если у
  заменяемой карты создатель не записан, бот спрашивает ревьюера. Значок Map Maker за фикс и за
  обновление не выдаётся. В игре «исправил» стал виден на этапе 2.

1. Новый `.msav` автора в посте с закрытым кейсом открывает кейс-обновление. Тег возвращается в
   `Waiting`, бот отвечает в посте «получена ревизия N, ждёт проверки». В `payload` — номер
   ревизии и номер предыдущего кейса.
2. Карточка обновления: где стоит прошлая версия и какая, список ревизий с номерами кейсов, что
   изменилось по сравнению с прошлой (размер файла, размеры карты, ядра по командам, число
   патчей). Данные прошлой ревизии уже лежат в её кейсе.
3. Кнопка называется «Обновить», сервер и целевое имя подставлены заранее.
4. «Принять» / «Обновить» — одна панель вместо цепочки вопросов: выбор сервера, строка «новая
   карта → `file.msav`» или «заменит `x.msav`», одно подтверждение, в котором перечислены ошибки и
   незавершённые проверки.
5. Кнопка «На доработку»: причина уходит автору, кейс остаётся открытым, пост не блокируется,
   новый файл перепроверяется сам, как сейчас для открытого кейса.
6. `/maps upload` внутри поста с открытым кейсом: если файл совпадает с проверяемым, бот ведёт
   через кейс, а не мимо.
7. Кнопка «Откатить на ревизию …» для ревьюера.
8. `/maps review` запускает ревью обновления и в старых постах; ревьюер может указать, какой
   установленный файл этот пост заменяет, — так привязываются карты, поставленные до системы.
9. Значок Map Maker при обновлении повторно не запрашивается, строка про ожидающий значок
   уходит с карточки в заметку.
10. Тексты исхода для автора: «обновление принято» отдельно от «карта принята».

Что при этом придётся поправить в ядре кейсов:

- `intake` ищет кейс по `map:<thread id>` и возобновляет его, даже закрытый
  (`cases/flows/maps.py:178`). Нужен поиск «активный кейс поста, иначе последний».
- Восстановление после сбоя сверяет имя файла из аудита с именем вложения
  (`cases/actions.py:377-386`). При замене целевое имя отличается от имени вложения, поэтому в
  `payload` появляется отдельное целевое имя, и сверяется оно.
- Теги поста определяет последний кейс поста, а не любой.
- Поиск ревью по хэшу для ссылки из `/map` (`cases/store.py:133`) уже берёт последний кейс —
  менять не нужно.

### Этап 2 — защита на сервере, протокол и плагин

Реализован полностью. Протокол 0.19.0, подробности — в
[map-discord-attribution.md](map-discord-attribution.md):

- Условная запись: `expectedContentHash`/`expectAbsent` в источнике файла и
  `expectedContentHash` в `maps.remove.request`, статус `conflict`. Бот берёт ожидание из списка
  карт, который видел ревьюер (`/maps upload`, принятие заявки, `/maps rollback`, `/maps remove`,
  «Вернуть»); для принятия заявки ожидание фиксируется при выборе цели.
- Корзина: `<custom maps>/.trash`, `maps.trash.retention_days`/`max_entries`, RPC
  `maps.trash.list` и `maps.restore` (с атрибуцией), команда `/maps trash <server>`. «Вернуть»
  сначала просит сервер вернуть свою копию, иначе грузит копию из Discord.
- В `discordUpload` — `caseNumber`, `threadId`, `revision`, `fixedBy`: в игре видно, кто
  исправил и из какого поста карта; в `/maps list` — 🔧 и «рев. N».
- Пункт 5: тест на перезапись играемой карты есть (`MapTransportTrashTest`).
- Пункт 4, несколько серверов (`map_installs.py`, без изменений протокола). Где стоит карта
  поста, бот узнаёт у самих серверов: файл, в атрибуции которого `threadId` этого поста. Конвейер
  кейса не менялся — одна внешняя операция и одна запись аудита на выбранный сервер. Если карта
  поста стоит и на других серверах, «Обновить» один раз спрашивает «обновить и их / только этот»;
  после закрытия кейса та же ревизия пишется на каждый другой сервер отдельно (своё ожидание
  хэша, свой аудит, у каждого сервера остаётся свой создатель), в пост уходит одна заметка с
  результатом по каждому серверу. Частичный успех не трогает принятую заявку: сервер, который не
  обновился, повторяют командой `/maps install <server> [replace]` в посте. Она же ставит
  принятую ревизию на новый сервер: файл из поста обновляется на месте; если его нет, карта
  ставится под принятым именем, а при похожей карте на сервере ревьюер называет её в `replace`.
  Файлы, загруженные до 0.19.0 (без `threadId`), так не находятся — их сначала привязывают через
  `/maps review [server] [replaces]` или обновляют `/maps install … replace:`.
- Решение 5, заморозка (`map_freezes.py`, коллекция `map_freezes`): `/maps freeze [server]
  [reason]` и `/maps unfreeze <server>`. Заморозка не запрещает, а предупреждает: принятие заявки,
  `/maps upload`, `install`, `rollback` и `remove` сначала показывают, кто и почему заморозил, и
  ждут подтверждения; автоматическое обновление других серверов замороженный пропускает.
  «Вернуть» после удаления и `/maps trash` не предупреждают — они отменяют только что сделанное
  изменение. Не прочитанная из базы заморозка не мешает изменению (предупреждение — подсказка).

1. Условие в `maps.upload.request` и `maps.remove.request`: «заменяю / удаляю файл с таким-то
   SHA-256». Если на диске уже другое, сервер отвечает новым статусом `conflict` и ничего не
   трогает. Закрывает гонку между тем, что видел ревьюер, и тем, что лежит на сервере.
2. Корзина на сервере вместо удаления и перезаписи (срок хранения в конфиге) и `maps.restore`.
3. Номер кейса, пост и номер ревизии в `map_uploads`, чтобы игровое меню и `/maps list`
   показывали версию и дату обновления.
4. Установка на несколько серверов одним действием. Самая рискованная часть: конвейер действий
   кейса рассчитан на одну внешнюю операцию с одной записью аудита, а здесь нужны запись на
   каждый сервер, частичный успех и повтор только для оставшихся.
5. Проверить в тесте перезапись файла карты, которая сейчас играется.

Изменения протокола аддитивные (минорная версия); порядок выката — как в
[map-discord-attribution.md](map-discord-attribution.md): протокол, серверы, бот.

### Этап 3 — статистика по идентичности карты

Сделано без миграции данных: запись статистики принадлежит файлу, под именем которого она
сохранена, пока этот файл установлен. Поиск по «название + автор» (для переименованных файлов)
такую запись другому файлу больше не отдаёт — второй файл с тем же названием и автором получает
свою запись. Правило одно на все пути: `findOrCreate` (голоса, RTV, итоги игры),
`findExistingAsync` (меню карт), список для Discord (`maps.list`) и выбор следующей карты
(`SmartMapSelector`, раньше брал статистику по ключу `name|author|mode`). Записи без имени файла
(старые, `"Unknown"`) ведут себя как раньше. Существующие записи не меняются; у второго файла
лайки начинаются с нуля, у первого остаются.

Затем сделан перевод на карту как сущность, с ключом по карте (посту), а не по «название + автор»
и не по slug. Это закрывает пункт 6 раздела 2 и политику связывания ревизий, которую
[спецификация идентичности](map-identity-and-reactive-ui-design-spec.md) оставила открытой.

**Что такое карта.** Карта — это пост на форуме: все файлы, которые ревью этого поста
установило, на любом сервере и под любым именем, — ревизии одной карты. Связь берётся только из
атрибуции загрузки (`map_uploads.upload.threadId`, её пишет бот при загрузке из заявки, этап 2).
Никогда не связываем по названию, автору, slug или хэшу: у двух разных карт может совпасть
название, а у каждой ревизии свой хэш. Ключи (`map/domain/MapKeys.java`):

- `post:<threadId>` — файл, установленный ревью поста;
- `file:<имя в нижнем регистре>` — файл без поста (загружен вручную или до этапа 2) — карта
  сама по себе;
- `record:<id>` — старая запись без имени файла (`"Unknown"`) — тоже сама по себе;
- имя файла, которое на разных серверах установили ревью двух разных постов, неоднозначно:
  такие записи ни к какому посту не привязываются (остаются `file:`), в лог пишется
  предупреждение.

**Модель данных.** Записи `maps` (файл + режим) остаются моделью записи: голоса, игры и
`SmartMapSelector` ссылаются на их id, и переписывать ссылки не нужно. `map_entities` —
производная проекция (`database/repository/MapEntityProjection.java`): по одному документу на
карту, с полями `map_key` (уникальный частичный индекс), `thread_id`, `file_names`,
`file_names_lower` (индекс) и суммами по всем записям. Ничто на неё не ссылается, удаление
коллекции ничего не теряет, пересборка идемпотентна и может идти на любом сервере.

**Когда пересобирается.** Миграция `V9__RebuildMapEntitiesByMap` удаляет документы v3 (без
`map_key`, сгруппированные по slug), создаёт индексы и собирает коллекцию заново; `V3` в истории
не меняется. Полная пересборка (`MapEntityProjection.rebuild`) идёт и при каждом старте сервера.
После загрузки, удаления или восстановления файла `service/map/MapEntities.refresh(fileName)`
обновляет только карты этого файла — ту, к которой он относится теперь, и ту, к которой относился
до изменения (`MapEntityProjection.update`): читает атрибуцию загрузок (по строке на сервер и
файл) и записи статистики только этих карт. Обновления идут на рабочем потоке хранилища, имена,
пришедшие во время обновления, обрабатываются следующей пачкой; в режиме только для чтения
ничего не пишется. Гонка двух серверов на вставке одного ключа разрешается повтором без upsert;
удаление карты (полная пересборка или пустая карта при обновлении) трогает только документы,
записанные до начала своего чтения, поэтому не стирает карту, которую другой сервер только что
записал по более свежим данным (часы серверов должны примерно совпадать). Запись, чьё имя файла
отличается от известных карте имён только регистром, подхватит следующая полная пересборка.

**Что изменилось для игроков и ревьюеров.** В `maps.list` (Discord: `/maps list`, выбор карты в
меню бота) лайки, дизлайки и репутация файла — это суммы по всей карте: по всем её ревизиям и
режимам. Популярность и интерес остаются по файлу и текущему режиму — они про то, как карта
играется здесь. Обновление карты новым файлом (этапы 1–2) больше не обнуляет её рейтинг в
списке, даже если имя файла поменялось. Если чтение карт не удалось, список отдаёт числа записи
файла, как раньше. Внутриигровые меню, голосования и выбор следующей карты остаются по записи
файла: голос виден сразу, и выбор не зависит от проекции.

**Известные края.** Игрок, голосовавший за две ревизии одной карты, учтён дважды (голоса лежат
на записях, а не на карте). Карта, у которой нет ни одного файла с постом, не связывается со
своей переименованной копией — для этого нужен пост. Откат — откат плагина: записи `maps` не
менялись, старая версия просто не читает `map_entities`.

## 6. Решения владельца

| № | Вопрос | Рекомендация |
| --- | --- | --- |
| 1 | Лайки и статистика при обновлении | По умолчанию сохраняются: замена ставит файл под прежним именем. Владелец не возражал, но отдельно не подтверждал |
| 2 | Отклонение | **Принято:** «Отклонить» закрывает заявку, пост не блокируется; есть «На доработку» |
| 3 | Исправление чужой карты. Сейчас файл принимается только от автора поста | **Принято:** исправивший создаёт свой пост, ревьюер выбирает «заменяет X»; создатель — оригинальный, исправивший помечен отдельно |
| 4 | Несколько серверов | **Принято при реализации:** заявка пишет на один сервер, остальные с картой поста обновляются после неё по одному (по выбору ревьюера), повтор — `/maps install` |
| 5 | Заморозка сервера («этот сервер пока не трогать») | **Принято при реализации:** `/maps freeze <server>` с причиной; установка и удаление предупреждают и ждут подтверждения |
| 6 | Как связывать ревизии одной карты | **Принято при реализации:** только по посту из атрибуции загрузки (`threadId` на любом сервере); без поста файл — отдельная карта; имя, установленное двумя постами, не связывается. Не по slug, названию или хэшу |
| 7 | Записи, разделённые по режимам | **Принято при реализации:** остаются моделью записи (на них ссылаются голоса и игры); карта — производная проекция `map_entities`, без переноса ссылок |
| 8 | Что показывает рейтинг | **Принято при реализации:** `maps.list` — лайки, дизлайки и репутация по всей карте (все ревизии и режимы); популярность и интерес — по файлу и режиму; меню в игре и голосования — по файлу |
